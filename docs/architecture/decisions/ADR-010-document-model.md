# ADR-010: The document model: references by id, variants as override sets, and the override shape

- **Status:** Accepted. It amends ARCHITECTURE §4.1 and §4.4 where they are silent or show a name where the file
  holds an id; only a person edits ARCHITECTURE.md, so the amendments live here until that happens.
- **Date:** 2026-10-12
- **Written by:** Prompt 8 (vellum-types II).
- **Evidence:** `crates/vellum-types/src/{document,variable,style,component,value,node}.rs`; tests in
  `crates/vellum-types/tests/{document,variables,components,styles,variable_properties,value,nodes,roundtrip}.rs`;
  `docs/format/` (the JSON Schema and the reference page, generated by `scripts/gen-format.mjs`); the Prompt 7
  note in `reports.md` that left the variable key open for this prompt to decide.

## Context

Prompt 7 typed the nodes and left three things for Prompt 8. The first was what a variable reference names. The
ARCHITECTURE examples write `{"$var": "color/primary"}`, a name path, while §4.1 keys `variables` by id. Every other
reference in the file is an id (`componentId`, `asset`, `textStyle`, a `NodeId` target, `Slot.suggested`). The
second was what variants are, since §4.1 names "variants" but does not define them. The third was the shape of
overrides, which Prompt 7 kept as untyped JSON.

Two things in the product decide the first point. The git merge driver (`vellum merge-driver`, Prompt 60) and
multiplayer (Prompts 63–64) both merge concurrent edits. A name reference breaks under them: one branch renames
`color/primary` while another adds a node that uses it, and the merge leaves a reference to a name that no longer
exists. Loro, the CRDT behind `DocStore` (ADR-004), has the same problem. An id does not change when a variable is
renamed, so the same merge stays clean.

## Decision

1. **A `$var` reference names a variable by its `VariableId`**, in `{"$var": "<id>"}`. An alias in a variable's
   values (`{"$alias": "<id>"}`) does the same. The variable's `name` (a path such as `color/primary`) is for people
   and tools; the id is the reference. Agents and tools accept names and resolve them to ids at their own boundary,
   as `replace_properties` will accept `$color/text`. A value that is a path is refused at parse time, because ids
   never hold a slash (guide §9).
2. **Variables are one tagged kind per type** (`color`, `number`, `string`, `boolean`). Each reads its literals as
   its own type, so a string variable keeps `#ff0000` as the text it is. An entry is a literal (`value`) or an alias
   (`$alias`), never both, with an optional `when` of theme axis values. Choosing the entry that applies (last
   match wins) is resolution (Prompt 16).
3. **A component's variants are override sets on its one node tree.** A variant lists a value for every variant axis
   and carries the overrides it applies to the tree. The variant whose values equal an instance's `variant` choice
   applies. There is no second copy of the tree per variant.
4. **An override is exactly one of three forms**, written with one key: `props` (a `NodePatch`), `replace` (a node)
   or `children` (a list of nodes). A `NodePatch` is a JSON object whose keys must each be a property some node has
   (`NODE_PROPERTIES`, checked against the schema by a test). It cannot set the `id` or the `children`.
5. **Props are typed declarations and literal values.** A component declares `boolean`, `text` or `number` props
   with a default of that type. An instance sets literal `Scalar` values. Which node a prop drives is **not decided**
   here (see Revisit when).
6. **Sections keep their order where order is meaningful.** Pages are a list; variables, styles, fonts, components,
   themes and imports are maps keyed by id or alias, written sorted, so the same document always prints the same
   bytes (Invariant 5).

## Costs and risks accepted

- A reader of a `.vellum` file sees an id where ARCHITECTURE's example shows a name. The variable's own entry holds
  the name, and the generated reference page explains it. Diffs of a fill that uses a variable show an id.
- The `NodePatch` values are JSON, checked against the node's own kind only when the patch is applied (Prompt 17).
  At load time the file only proves the keys are real property names. A typed patch per node kind was judged too
  large for this prompt; it can be generated later from the same node structs if the schema needs it.
- Variant overrides are applied in the resolver, so a component's variants are not visible in its own tree. The
  inspector must show them (DESIGN C16).
- Generic instantiations get schema names such as `Value2` and `VariableValue3`, because schemars numbers them. The
  reference page reads them as they are; a human who wants names can add `schemars` renames later.

## Not decided

- **How a prop reaches a node.** Options: a `{"$prop": "<name>"}` reference beside `$var` on bindable fields (it
  widens `Value<T>`, and text content is a `Vec<TextRun>` with no `Value` today); or a binding list on each prop that
  names a node path and a property. Prompt 17 decides, and the format changes if it adds one.
- **Validation** (every alias resolves to a variable of the same type, alias cycles, unique names, each variant names
  every axis, a theme's first value is its default, a prop's default matches its type). Prompts 10, 11 and 16 own it.
- **Library variables.** A library's variables are reached through its import, not copied, so a `$var` in a document
  names a variable of that same document. Whether paste copies variables into the destination (ARCHITECTURE §4.4)
  is Prompt 17's.

## Revisit when

- A person decides how props bind to nodes (the first item above). That decision may change the format before v1.
- Merge or multiplayer testing (Prompts 15, 60, 63–64) shows that a rename and a use of the same variable still
  conflict under ids. The reference would then need a stable key of its own.
- Users find the id references unreadable enough that the reference page and the tools cannot cover it. Then a
  readable name can be stored beside the id, and the rename rule written down.
- A typed override per node kind becomes necessary for the resolver or for agents (see the costs above).
