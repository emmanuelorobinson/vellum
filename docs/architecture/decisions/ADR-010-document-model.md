# ADR-010: The document model: references by id, variants as override sets, and the override shape

- **Status:** Accepted. It amends ARCHITECTURE §4.1 and §4.4 where they are silent or show a name where the file
  holds an id; only a person edits ARCHITECTURE.md, so the amendments live here until that happens.
- **Date:** 2026-10-12
- **Written by:** Prompt 8 (vellum-types II).
- **Evidence:** `crates/vellum-types/src/{document,variable,style,component,value,node}.rs`; tests in
  `crates/vellum-types/tests/{document,variables,components,styles,variable_properties,value,nodes,roundtrip}.rs`;
  `docs/format/` (the JSON Schema and the reference page, generated by `scripts/gen-format.mjs`); the Prompt 7
  note in `reports.md` that left the variable key open for this prompt to decide.

## Context

Prompt 7 typed the nodes and left three things for Prompt 8. The first was what a variable reference names. The
ARCHITECTURE examples write `{"$var": "color/primary"}`, a name path, while §4.1 keys `variables` by id. Every other
reference in the file is an id (`componentId`, `asset`, `textStyle`, a `NodeId` target, `Slot.suggested`). The
second was what variants are, since §4.1 names "variants" but does not define them. The third was the shape of
overrides, which Prompt 7 kept as untyped JSON.

Two things in the product decide the first point. The git merge driver (`vellum merge-driver`, Prompt 60) and
multiplayer (Prompts 63–64) both merge concurrent edits. A name reference breaks under them: one branch renames
`color/primary` while another adds a node that uses it, and the merge leaves a reference to a name that no longer
exists. Loro, the CRDT behind `DocStore` (ADR-004), has the same problem. An id does not change when a variable is
renamed, so the same merge stays clean.

## Decision

1. **A `$var` reference names a variable by its `VariableId`**, in `{"$var": "<id>"}`. An alias in a variable's
   values (`{"$alias": "<id>"}`) does the same. The variable's `name` (a path such as `color/primary`) is for people
   and tools; the id is the reference. Agents and tools accept names and resolve them to ids at their own boundary,
   as `replace_properties` will accept `$color/text`. A value that is a path is refused at parse time, because ids
   never hold a slash (guide §9).
2. **Variables are one tagged kind per type** (`color`, `number`, `string`, `boolean`). Each reads its literals as
   its own type, so a string variable keeps `#ff0000` as the text it is. An entry is a literal (`value`) or an alias
   (`$alias`), never both, with an optional `when` of theme axis values. Choosing the entry that applies (last
   match wins) is resolution (Prompt 16).
3. **A component's variants are override sets on its one node tree.** A variant lists a value for every variant axis
   and carries the overrides it applies to the tree. The variant whose values equal an instance's `variant` choice
   applies. There is no second copy of the tree per variant.
4. **An override is exactly one of three forms**, written with one key: `props` (a `NodePatch`), `replace` (a node)
   or `children` (a list of nodes). A `NodePatch` is a JSON object whose keys must each be a property some node has
   (`NODE_PROPERTIES`, checked against the schema by a test). It cannot set the `id` or the `children`.
5. **Props are typed declarations and literal values.** A component declares `boolean`, `text` or `number` props
   with a default of that type. An instance sets literal `Scalar` values. Which node a prop drives is **not decided**
   here (see Revisit when).
6. **Sections keep their order where order is meaningful.** Pages are a list; variables, styles, fonts, components,
   themes and imports are maps keyed by id or alias, written sorted, so the same document always prints the same
   bytes (Invariant 5).

## Costs and risks accepted

- A reader of a `.vellum` file sees an id where ARCHITECTURE's example shows a name. The variable's own entry holds
  the name, and the generated reference page explains it. Diffs of a fill that uses a variable show an id.
- The `NodePatch` values are JSON, checked against the node's own kind only when the patch is applied (Prompt 17).
  At load time the file only proves the keys are real property names. A typed patch per node kind was judged too
  large for this prompt; it can be generated later from the same node structs if the schema needs it.
- Variant overrides are applied in the resolver, so a component's variants are not visible in its own tree. The
  inspector must show them (DESIGN C16).
- Generic instantiations get schema names such as `Value2` and `VariableValue3`, because schemars numbers them. The
  reference page reads them as they are; a human who wants names can add `schemars` renames later.

## Not decided

- **How a prop reaches a node.** Options: a `{"$prop": "<name>"}` reference beside `$var` on bindable fields (it
  widens `Value<T>`, and text content is a `Vec<TextRun>` with no `Value` today); or a binding list on each prop that
  names a node path and a property. Prompt 17 decides, and the format changes if it adds one.
- **Validation** (every alias resolves to a variable of the same type, alias cycles, unique names, each variant names
  every axis, a theme's first value is its default, a prop's default matches its type). Prompts 10, 11 and 16 own it.
- **Library variables.** A library's variables are reached through its import, not copied, so a `$var` in a document
  names a variable of that same document. Whether paste copies variables into the destination (ARCHITECTURE §4.4)
  is Prompt 17's.

## Revisit when

- A person decides how props bind to nodes (the first item above). That decision may change the format before v1.
- Merge or multiplayer testing (Prompts 15, 60, 63–64) shows that a rename and a use of the same variable still
  conflict under ids. The reference would then need a stable key of its own.
- Users find the id references unreadable enough that the reference page and the tools cannot cover it. Then a
  readable name can be stored beside the id, and the rename rule written down.
- A typed override per node kind becomes necessary for the resolver or for agents (see the costs above).

## Prompt 15: conflict nodes, ops for every part of a document, diff and merge

- **Date:** 2026-10-12
- **Written by:** Prompt 15 (diff → ops, three-way merge, merge-driver core).
- **Evidence:** `crates/vellum-core/src/{diff,merge}/` (with their unit tests), `crates/vellum-core/tests/diff_merge.rs`
  and `tests/common/mutate.rs` (property tests over random branches of every fixture document),
  `crates/vellum-core/fuzz/` (cargo-fuzz target `merge`), `crates/vellum-core/src/ops/tests/document.rs`, the
  contract check `document_parts` in `crates/contracts/src/suites/doc_store.rs`, and the regenerated `docs/format/`.

### Decision

1. **A `conflict` node kind, the 19th** (ARCHITECTURE §4.5 asks for "a conflict marker node"; DESIGN C22 shows one).
   It takes the conflicted node's place and id and has the common fields (copied from one version, so it shows where
   the node was), `ours` and `theirs` (that side's version of the node without children; absent when that side
   removed it), `properties` (what both sides changed; `type` when the kind is one of them; empty for a removal) and
   `children` (the node's merged children, which stay live in the document). Choosing a version is
   `Op::Replace { id, node: version }`, which may reuse the id. Versions are not walked for ids, so the id is not a
   duplicate. A conflict node may stand where its node stood and holds anything, including on a slides page and in a
   boolean. The format version stays 1: nothing has been released.
2. **Every part of a document is reachable by ops**, because an external change is applied as ops (Invariant 1, §4.5).
   New ops: `InsertPage`, `DeletePage`, `UpdatePage` (name, kind), `MovePage`, `SetShell` (meta, imports, themes,
   styles, fonts as one value, `ops::Shell`), `SetComponent` (add, replace with its tree, remove) and
   `UpdateComponent` (name, props, variants; the tree stays). New edits: `InsertPage`, `RemovePage`, `SetPage`,
   `MovePage`, `SetShell`. `ChangeSet` gains `pages`, `components` and `shell`; `Kept` gains `Page` and `Shell`; the
   Guard treats removing a leased frame's page, or changing its kind, as touching the frame.
3. **References are checked once per transaction**, against the document it leaves (instances, override paths,
   slots). A transaction is all or nothing, so only its end has to be valid, and ops can come in any order that
   gets there; the diff relies on it. When the end is invalid, the transaction is planned again with the same ids,
   checking after every op, so the error still names the op that first broke a reference. Variable references are
   still checked as each op is planned. It also makes planning cheaper (below).
4. **Diff** (`vellum_core::diff::diff`): a node with the same id, kind and tree (the pages, or one component) in both
   documents is the same node, so it gets an `Update` of the properties that differ (`null` for one back at its
   default), a `Move` to a new parent, a `Reorder` among siblings. Only nodes that are new, gone, or changed kind or
   tree are inserted and deleted, as whole subtrees without what lives on inside them. A component whose root
   changes is set whole. The ops are ordered so every step is accepted (the module comment lists the order).
5. **Merge** (`vellum_core::merge::merge`), three-way by node id and property: what one side changed is taken; what
   both changed differently is a conflict. Same property of one node: a conflict node, each version carrying every
   non-conflicting change from both sides. Removed on one side, changed (or changed inside) on the other: the change
   wins; the topmost removed node becomes a conflict node with no version for the side that removed it, and the
   other side's whole version of what was under it lives on. Where no node can hold both (both moved one node to
   different places, both reordered the same children differently, one entry of the document such as a variable,
   style, page or the name changed both ways): ours is kept and the conflict is reported. Inserts at the same place
   are ordered by id, so a merge without conflicts does not depend on which side is ours. Moves that make a cycle
   put its nodes back where ours has them. After assembly: a variable or component one side removed and the other
   uses is kept; an instance whose overrides no longer resolve (one side changed the component, the other the
   instance) becomes a conflict node; a slides page that would hold what it cannot becomes a canvas. The result is
   checked like any document; when it cannot be made valid, `merge` returns an error and the caller keeps ours.
6. **History fixes found on the way** (Prompt 14's rules, now covering pages): redo protects only other people's
   later work (since an undo, the actor's own changes can only be redos, because a new change clears redo); making
   a variable or component is not "changing it since"; a component's change of name, props or variants does not
   count as replacing its tree. All three were bugs that `document_parts` found on the in-memory store first.

### Numbers

Apple M5 Pro, release, the Prompt 14 benchmark (`crates/adapters/doc-loro/tests/undo_cost.rs`, 10,000 nodes,
200-node batch, medians of 7): planning the batch went from about 292 ms to **13.2 ms**; plan and store 24.5 ms;
undo 15.0 ms and redo 15.3 ms (Prompt 14: 14.5 ms; budget 16). The diff and merge of a 10,000-node document were not
timed; the diff plans each op as it makes it, and an insert still lists every id, so a diff with many inserts into
a large document costs inserts × nodes.

### Costs and risks accepted

- Conflicts with no node to hold them (moves, orders, document entries) live only in the merge's report; the file
  keeps ours, and theirs stays in Git (`MERGE_HEAD`). The editor (Prompt 53, the C22 work) has to show them from
  the report.
- A conflict node's children are live, and ops may insert into it, so work can continue around a conflict.
- An override conflict is coarse: the whole instance becomes a conflict node, not the one override.
- A kind change on one side against any property change on the other is a conflict of whole versions.

### Not decided

- Who resolves report-only conflicts, and how "Ask agent to merge" frames a conflict for an agent (DESIGN C22).
- `vellum merge-driver` itself (exit codes, the report's format, `.gitattributes`): Prompt 60.

### Reference reading

Graphite's `editor/src/messages/portfolio/document/document_diff.rs` (MIT OR Apache-2.0, commit
`7477cd2fab315494e4c2613bc446c707733e6e7b`) diffs two node registries by id as set differences (missing, extra,
shared with differing payloads), then compares the shared ones field by field; it prints the result for a debug
check and produces no edits. Vellum keeps the shape (match by stable id, then per field) and changes the output: ops
in an order the op layer accepts, so an external change goes through the one write path. Nothing was ported.

## Prompt 16: resolving variables, theme axes and aliases

- **Date:** 2026-10-14
- **Written by:** Prompt 16 (Resolver I).
- **Evidence:** `crates/vellum-core/src/resolver/variables/` (with its unit tests in `tests/`),
  `crates/vellum-core/tests/resolver_cache.rs` (cached equals fresh over random edits), `crates/vellum-types/src/bindings.rs`,
  and the binding cases in `crates/vellum-core/src/resolver/variables/tests/bind.rs`.

### Decision

1. **A theme is one value on every axis.** `Theme::defaults` takes the first value of each axis (an axis with no values
   has none). A frame's `theme` replaces the axes it names, for itself and everything below, and only those. A choice
   naming an axis or value the document lacks is a typed `ThemeError`; a tree resolution ignores that one choice,
   applies the rest, and reports it as a `Problem` on the node (`theme.Mode`).
2. **The last entry that applies wins.** An entry applies when every axis in its `when` has that value in the theme;
   no `when` always applies; an axis the document lacks never matches. Position decides, not specificity: a later,
   broader entry beats an earlier, narrower one. No entry applying is `VariableError::NoValue`.
3. **An alias is followed under the same theme**, so the target picks its own entry. A cycle is an error only along the
   entries the theme selects (`Cycle` names the loop, first and last the same variable); the op layer still refuses
   any alias loop on any entry when it is set, so a cycle here means a file, merge or older version the ops never
   saw. A missing target, or one of another type, is `Unknown` / `AliasType`.
4. **Types are checked where a binding is made.** Every property that takes a variable has a type: opacity a number,
   `visible` a boolean, a fill's colour a colour, an icon's name a string, a script input any variable (a colour
   arrives as the text `#RRGGBB`, because a script input is a boolean, number or text), a shader uniform a boolean,
   number or colour. `vellum_types::Bindings` walks a node's places with that type (one walk for reading, one for
   writing, from one macro), so the op layer and the resolver share the list. Insert, replace, update, wrap, page,
   component and shell ops, and a variable changing type while something uses it, are refused with
   `OpErrorKind::BindingType`, at a path such as `patch.fills[0].color`. `check_document` reports the same.
5. **Like references, types are checked once per transaction**, against where it ends, because the diff changes a
   variable's type before it rebinds what used it. When the end is wrong the transaction is planned again, and the
   replay refuses only that binding error, so the error names the op that caused it and not a passing state. A
   problem the document already had, in the same place, is not the transaction's: renaming a layer is not the
   moment to refuse a binding a file arrived with.
6. **A resolved tree** is `ResolvedNode`: the node's own properties without children, every reference that resolved
   replaced by its value, the theme in force, whether it is shown (`visible`, a boolean variable can decide), and its
   resolved children shared by `Arc`. A reference that cannot be resolved stays a reference and is listed in
   `problems`, so nothing is drawn from a guess; an unresolved visibility flag counts as shown.
7. **The cache is per node, kept good by a dirty set.** An entry is good while the node's content did not change (the
   `ChangeSet` names the nodes that did), the theme it inherited is the same (compared on the way down), and none of
   the variables it read changed (an index from variable to readers; a node's reads include every variable on the
   alias chains it followed, and a variable it asked for that did not exist). A change to the theme axes drops
   everything. A `ChangeSet` does not name the parent of an inserted, removed or moved node, so a parent is rebuilt
   whenever a child's resolved node is not the one it held. That makes the walk visit every node, but only dirty
   ones are recomputed, and a rebuilt parent reuses its own resolved properties.

### Numbers

`cargo test resolver::variables` runs 51 unit tests and the property test (300 random cases and a fixed corpus of 400
seeds; 30,000 seeds were run once, in release, 3.4 s). The property test was checked by breaking the cache four ways
(variable readers not evicted, inherited theme not compared, updated nodes not evicted, a parent reused after its
children changed); each made it fail. Nothing was timed against a large document.

### Costs and risks accepted

- The walk visits every node on every resolve. It is a hash lookup and a pointer comparison per node, with no
  allocation, but it is O(nodes) where a skip of untouched subtrees would be O(changes). Skipping needs the
  ChangeSet to name parents or the cache to hold parent links for the new structure; neither is done.
- Props overrides are plain JSON, so a `$var` inside one is not type-checked until Prompt 17 applies it. A variable
  inside a props override of the wrong type is therefore not refused today.
- A script input bound to a colour variable receives text. A script that wants the channels has to parse it.
- `ResolvedNode::visible` is the node's own flag. Applying a hidden ancestor is left to the reader of the tree.

### Not decided

- Resolution of instances, overrides, slots and libraries (Prompt 17). The cache is keyed by node id, and a component
  change will have to reach its instances there.
- Whether the resolved value of a style (`textStyle`) belongs on the resolved text node or beside it (Prompts 19, 21).
